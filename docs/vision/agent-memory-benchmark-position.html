On evaluating agent memory

The memory we
don't measure.

Our agents forget across sessions, and the leaderboards they compete on cannot see it. We think that is a problem worth naming, and a benchmark worth owning.

The pitch, in one breath

An agent harness — Claude Code, Codex, Cursor and their peers — is at heart a general-purpose engine. What turns one into a paralegal, an incident responder, a financial analyst or a clinician's assistant is grounding: the skills, commands, sub-agents, MCP servers, scripts and hooks that pin a generic substrate to a domain. Memory sits beneath all of it. Whatever the domain, the harness must retain what it established last session — the chosen approach, the rejected alternative, the reason — and today it largely does not.

Yet the benchmarks these harnesses compete on measure single-task resolution and say nothing about what the agent carries into tomorrow. Memory is studied prolifically, but either in conversational isolation divorced from real work, or — in the one task-grounded case we have — only for code. We propose to close the gap deliberately: adopt the mature suites for what they cover, and build the thin missing layer — a harness-level, domain-pluggable, task-grounded memory benchmark that scores memory through real work completed across sessions in more than one domain, and that measures the dimension everyone underweights: whether the agent actually used the memory it was given. Memory is not a feature flag. It is a cross-cutting quality attribute of the harness itself, and it deserves a scorecard.

01

Monday morning, every Monday

A practitioner closes a session on Friday having settled three things — a chosen approach, the reason an alternative was rejected, and a piece of work to leave alone rather than touch. On Monday she opens a fresh session and re-explains all three. The agent is bright and capable and has, between Friday and Monday, learned nothing. She might be a developer settling an architecture; she might equally be an analyst settling a methodology or a support lead settling an escalation policy. The harness underneath is the same engine, and the amnesia is identical.

It is worth being precise about why these harnesses matter as a class. They are not domain tools that happen to generalise; they are general engines that are, today, most visibly pointed at code. Ground one with the right skills, commands, sub-agents, MCP servers, scripts and hooks and it becomes a paralegal, a researcher or an operations analyst by the afternoon. That grounding is domain-specific by design. The memory beneath it is not — and it is the one layer none of those extension surfaces can supply on the harness's behalf.

This is the quiet tax on agentic development, and it is paid in the same currency every day: re-stated architecture, re-pasted context, re-discovered bugs. The industry's answer so far has been the static instruction file — CLAUDE.md, AGENTS.md, .cursorrules — a sticky note pinned to the project. These files help, but they are written by hand, they go stale, and they run out of room at a few thousand characters. A directory of sticky notes is not memory; it is a workaround for its absence.

The interesting question is not how to give an agent memory. A dozen tools and research systems now do that. The interesting question is the one nobody answers when they ship a harness: how good is its memory, measured against what?

02

A non-functional concern — but only half of one

It is tempting to file memory under non-functional requirements, alongside latency and uptime, and there is truth in that: memory has genuine non-functional dimensions — the tokens it costs to carry, the latency it adds to retrieval, the way it scales as the store grows, the privacy surface it opens. But the framing is only half right, and the missing half is where the value lives.

Memory also flips functional outcomes. A multi-session task — a refactor, an investigation, a long-running case — either succeeds or fails depending on whether the agent recalls the decision it made three sessions ago. The same prompt produces correct work or confident nonsense depending on what the agent remembers. Memory is therefore better understood the way we understand security or observability: a cross-cutting quality attribute that touches every capability, cannot be reduced to a single number, and cannot be bolted on after the fact. You do not benchmark security with one score, and you should not benchmark memory with one either.

03

What already exists — and what it misses

The research community has not been idle. There is a rich and fast-growing body of memory benchmarks, and we should stand on it rather than reinvent it. The shape of the field is clear once it is laid out:

The conversational suites. LoCoMo stretches dialogue across dozens of sessions and hundreds of turns; LongMemEval probes long-term interactive recall in assistant chats; MemBench separates factual from reflective memory and scores effectiveness, efficiency and capacity; MemoryAgentBench borrows from cognitive science to test retrieval, test-time learning, long-range understanding and selective forgetting. These are mature and well-designed. They are also, almost without exception, about talking — multi-session chat, not multi-session work, and rarely grounded in any real domain at all.

The one task-grounded entrant. Only recently has memory been measured inside real multi-turn agent work rather than chat — and, tellingly, the single benchmark that does so is grounded in software engineering, because that is where the harnesses were first pointed. LoCoBench-Agent turns thousands of engineering scenarios into multi-turn agent environments and reports a multi-session retention metric. Its verdict is the figure at the top of this page: retention parks itself around a third, for everyone, regardless of context-window size or compression strategy. There is no reason to expect a paralegal or an operations agent built on the same harness to fare better — and every reason, today, to expect it has simply never been checked.

The gap, stated plainly

The leaderboards the harnesses actually compete on are memory-blind.

Whatever domain a harness is grounded into, the board it competes on rewards resolving a task in a single sitting. It does not, and was never meant to, measure what the agent carries into the next session. So memory is either tested in conversational isolation that resembles no real workflow, or left off the boards that decide which harness "wins." Nobody ranks harnesses on memory. That is the opening.

04

Field notes: where memory earns or loses its keep

Abstractions persuade nobody. The case for measuring memory is made by the situations where its absence has a cost, or its presence a payoff — and they recur across every domain a single harness can be grounded into. A handful from the wild:

Retention · legal

The re-argued case theory

A litigation-support agent settled the case theory and the three precedents it rests on. The next session it asks counsel to restate the theory from scratch — and quietly drops one precedent in the retelling.

Conflict · support

The ghost of the old policy

A refund policy changed a fortnight ago. The support agent's memory still holds the old thresholds and confidently approves against them. The failure is not forgetting — it is remembering the wrong thing and never updating when the truth moved.

Cost · any domain

The context that ate the budget

An instruction or knowledge file balloons past twenty thousand tokens. The window is half-consumed before the agent does any real work, and most of those tokens are inert. Memory that cannot be carried cheaply cannot be carried at all.

Forgetting · sales

The flag that should have aged out

A "hold all outreach" flag from last quarter is still injected every session, long after the account reopened and asked to be contacted. Accretion without forgetting turns memory into clutter, and clutter degrades retrieval.

Grounding · any domain

The memory that was there but unused

The right past decision was retrieved and placed in context — and the agent ignored it, producing work that contradicts it. Recall is necessary but not sufficient. Did the agent act on what it remembered?

Privacy · health

The detail that persisted

A patient identifier slips into the memory store during one session and is silently surfaced in another, perhaps to a different user. A memory layer is also a data-retention surface, and evaluation must probe what it leaks.

05

The dimensions we would actually measure

If memory is a cross-cutting attribute, a single accuracy number betrays it. We would score a harness across seven orthogonal dimensions — most are partly covered by existing work; the last two are where the field is thin and where we would contribute.

R1

Retention

Does a fact or decision established N sessions ago still hold? The plain question, and still largely unsolved at long horizons.

Covered · LoCoMo, LongMemEval, LoCoBench-Agent

R2

Retrieval precision

For the task at hand, does the agent surface the right memory and not a plausible neighbour? Measured as precision, recall and ranking quality.

Covered · LongMemEval, MemoryAgentBench

R3

Update & conflict resolution

When the truth changes — a refactor, a reversed decision — does memory update and override the stale version, or persist a contradiction?

Partial · MemoryAgentBench

R4

Selective forgetting

Does the agent shed the obsolete and irrelevant rather than accreting forever? Forgetting is a feature, and a measurable one.

Partial · MemBench, MemoryAgentBench

R5

Efficiency & cost

The token budget and latency the memory layer imposes per turn. A correct memory that bankrupts the context window is not a usable one.

Partial · MemBench (efficiency axis)

R6

Capacity degradation

How performance erodes as the store grows from a hundred to a hundred-thousand observations. The scaling curve, not a single snapshot.

Partial · MemBench (capacity axis)

R7

Grounding & attribution

Did the agent actually use the memory it was given, and can the outcome be attributed to it? Recall without use is theatre. This is the frontier.

Gap · underweighted everywhere — our contribution

06

The procedure is the asset

Everything so far has quietly assumed one person remembering their own context. The enterprise breaks that assumption in the most valuable way — and it is a case our benchmark should be built to capture.

When a single plugin grounds a harness for an entire organisation, the memory worth keeping is often not what any one user said. It is how the harness solved the problem the first time, captured cleanly enough that the next user — and the thousandth — need not pay for the derivation again. Memory differs not only in what it holds (an episode, a fact, a procedure) but in whom it serves (one user, one agent, the whole organisation). The corner almost no benchmark occupies is the one that matters most here: shared, procedural, and de-identified — the canonical, personal-data-free procedure for a frequently-invoked, "fat-head" intent.

The payoff is concrete. Replay a vetted procedure and the same intent resolves faster, because the agent skips the exploration; cheaper, because it skips the re-derivation; and more deterministically, because it walks the same validated path every time. This is not caching an answer — it is caching a method, which is precisely why it transfers across users whose specifics differ. And it is a determinism lever in the exact sense that matters: a hot intent is lifted off free-form reasoning and set on a codified path, and the best of these procedures graduate into skills and commands. The harness's own grounding surfaces are, over time, fed by its procedural memory. Usage distils the procedure; vetting promotes it; reuse repays it — codification earned from traffic.

There is a catch, and it is the reason this needs a benchmark with a gate rather than a cache. Captured procedure is double-edged: the evidence is blunt that curated procedures lift agent success markedly, while self-generated ones accepted uncritically can degrade it by encoding wrong or over-specific heuristics. A procedure distilled from one user's lucky path can carry hidden assumptions that quietly mislead the next. So the question is not whether procedures can be reused — they can — but what a benchmark must establish before they are trusted:

Transfer across users — does a procedure distilled from one user's instance still solve the next user's instance of the same intent, or did it overfit? Measured across users, not within a single trajectory. The de-identification boundary — shared procedural memory must be provably devoid of personal data yet retain enough to remain useful; catching leakage across the personal-to-shared boundary is a first-class test, not a compliance footnote. Blast radius — a stale or wrong shared procedure does not inconvenience one user, it misleads everyone who invokes that intent at once, so the benchmark must score how quickly shared memory detects its own staleness and is retired. The determinism dividend — measure the variance, cost and latency a reused procedure removes, not only the accuracy it preserves, because faster, cheaper and repeatable is the entire point.

07

Our position

We do not need another conversational memory benchmark. We need to measure memory where real work happens — in whatever domain the harness has been grounded into — and to measure the part everyone skips. Concretely:

  1. Adopt, do not rebuild. The conversational suites already cover retention, retrieval and forgetting competently. We harness against them rather than duplicating them, and we cite their findings rather than re-deriving them.
  2. Build the thin missing layer: a harness-level, domain-pluggable, task-grounded benchmark. Memory should be scored through real multi-session work — a matter opened in one session and closed in another, a decision made early and tested late — not through chat question-answering. Crucially, we instantiate the same harness into several domains using the very surfaces that ground it — skills, commands, sub-agents, MCP servers, scripts, hooks — and measure memory across all of them, because memory is a property of the harness and must hold whatever it has been grounded to do. LoCoBench-Agent is the closest seed; we generalise its spirit beyond code to whole-workflow continuity across domains.
  3. Treat shared procedural memory as a first-class, gated mode. Where a plugin grounds a harness for an entire organisation, the canonical de-identified procedure for a fat-head intent is an asset worth measuring on its own terms — transfer across users, a provable personal-data boundary, and the variance, cost and latency it removes. And it is gated: the evidence is plain that curated procedures help and uncurated ones can hurt, so we score reuse with a vetting step, not without one.
  4. Make grounding and attribution first-class. The dimension the field underweights (R7) is precisely the one that matters to a practitioner: not "was the right memory retrievable" but "did the agent use it and was the result better for it." We instrument for causal attribution, not just recall.
  5. Publish a scorecard, not a number. Because memory is a cross-cutting quality attribute, we report a profile across the seven dimensions and surface it as a distinct axis alongside task-resolution leaderboards — so a harness can be strong on resolution and visibly weak on memory, and the difference is legible.
  6. Insist on reproducibility. Memory layers are stateful and non-deterministic; the corpus must be sandbox-reproducible and the protocol must pin the seeds, the store contents and the injection policy, or the leaderboard means nothing.
08

What could go wrong

A position is only honest if it names its own failure modes. Five are worth holding in view. Goodharting — optimise hard for recall@k and watch forgetting and cost regress; the scorecard exists partly to make this trade-off visible rather than hide it. Contamination — shared memory stores leak across agents and across evaluation runs, inflating scores; isolation must be part of the protocol. Reproducibility drift — a stateful, non-deterministic memory layer is hostile to clean measurement, and a sloppy harness will produce numbers nobody can reproduce. Privacy as an afterthought — if the benchmark never probes what the memory store retains and surfaces, it certifies a capability while ignoring its most serious liability. Blast radius — once a procedure is shared across an organisation, a poisoned or stale one misleads everyone who invokes that intent rather than one user, so the leverage that makes shared procedural memory valuable is precisely what makes its failures organisation-wide.

None of these is disqualifying. All of them are reasons the benchmark should be designed by people who take memory seriously as infrastructure — which is the argument for owning it rather than waiting for it.
